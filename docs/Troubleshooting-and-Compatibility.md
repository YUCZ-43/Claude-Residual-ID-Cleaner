## 1. System Compatibility Matrix / 系统兼容性矩阵

| Component | Minimum Requirement | Recommended | Notes |
| :--- | :--- | :--- | :--- |
| **Operating System** | Windows 10 (Build 19041+) | Windows 11 (Build 22621+) | 64-bit editions required. |
| **Primary Filesystem** | NTFS | NTFS | Relies on NTFS `FileIndex`, `VolumeSerialNumber`, and handle disposition. Non-NTFS (FAT32, exFAT, ReFS, SMB shares) fail closed. |
| **PowerShell Runtime** | Windows PowerShell 5.1 | PowerShell 7.4+ (`pwsh`) | Full compatibility across Desktop edition (CLR 4.0) and Core (.NET 8/9). |
| **User Privileges** | Standard User | Standard User | Runs under standard user context. Does NOT require Administrator privileges. |

## 2. Common Errors and Resolution / 常见错误与解决方案

### 2.1 Manifest Schema Version Error
**Symptom:**
```text
Unsupported manifest schema version (SchemaVersion 3 required)
```
**Cause:**
`CLEANUP-PLAN.md` was generated by an older version of the toolkit, has an invalid structure, or was modified after generation.

**Solution:**
Re-generate a fresh cleanup manifest using:
```powershell
.\ClaudeCleanup.ps1 -Plan
```
Use the newly emitted 64-hex SHA-256 hash when running `-Apply`.

---

### 2.2 Ownership Blocked (`BUILTIN\Administrators` or `OtherOwner`)
**Symptom:**
Target items are marked as `Blocked` with reason:
```text
Target is not owned by the current user (Owner: BUILTIN\Administrators)
```
**Cause:**
Artifacts created by elevated Command Prompt / PowerShell sessions (e.g., `npm install -g` run inside an Administrator terminal) inherit the `BUILTIN\Administrators` group SID as owner rather than your user account SID.

**Solution:**
The toolkit enforces a strict security policy: **it will never take ownership or mutate Windows ACLs**.
To clean administrator-owned components:
1. Review the specific path identified in `CLEANUP-PLAN.md`.
2. Uninstall the component using its official elevated installer (e.g., elevated `npm uninstall -g @anthropic-ai/claude-code`).
3. Or manually delete the specific administrator-owned folder in an elevated terminal.

---

### 2.3 Reparse Point Blocked (`ReparseBlocked`)
**Symptom:**
Target directory is marked as `Blocked` or `ReparseBlocked` with reason:
```text
Ancestor or child contains a reparse point (junction / symlink)
```
**Cause:**
The target path, one of its parent directories, or a child node within its tree is an NTFS directory junction, volume mount point, or symbolic link.

**Solution:**
The engine strictly refuses to traverse or delete reparse points to protect against directory traversal and link redirection attacks.
1. Inspect the path using:
   ```powershell
   Get-Item -LiteralPath "C:\Path\To\Item" -Force | Select-Object LinkType, Target
   ```
2. If the junction was created manually, remove the junction link using `cmd /c rmdir "C:\Path\To\Junction"` before running the cleanup engine.

---

### 2.4 Registry Access Blocked (`Requested registry access is not allowed`)
**Symptom:**
Browser Native Messaging key reports:
```text
Cannot inspect registry key: Requested registry access is not allowed.
```
**Cause:**
Group policy, third-party security software, or an app-container sandbox is restricting direct read/write access to `HKCU:\Software\Google\Chrome\NativeMessagingHosts` or `HKCU:\Software\Microsoft\Edge\NativeMessagingHosts`.

**Solution:**
Under the toolkit's 3-state model, access errors are classified as `Unknown` and marked `Blocked`. They are **never** assumed to be `Absent`.
- Verify you are running PowerShell under your regular interactive user session.
- Ensure security software is not blocking user-level registry reads.

---

### 2.5 PowerShell Script Execution Disabled
**Symptom:**
```text
File .\ClaudeCleanup.ps1 cannot be loaded because running scripts is disabled on this system.
```
**Cause:**
Windows PowerShell execution policy defaults to `Restricted`.

**Solution:**
Enable script execution for the current user without bypassing machine security:
```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```
Or execute within a single process scope:
```powershell
powershell.exe -NoProfile -ExecutionPolicy RemoteSigned -File .\ClaudeCleanup.ps1 -Audit
```

---

### 2.6 File In Use / Sharing Violation
**Symptom:**
Handle acquisition fails with sharing violation or process lock error during `-Apply`.

**Cause:**
An active process (`claude.exe`, `Claude.exe` Desktop, or `Code.exe`) is running and holding open file handles in `%APPDATA%\Claude` or `.claude`.

**Solution:**
1. Check running processes via:
   ```powershell
   .\ClaudeCleanup.ps1 -Audit
   ```
2. Close all Claude CLI sessions, Claude Desktop windows, and VS Code instances.
3. If background node or worker processes remain, terminate them via Task Manager.

---

### 2.7 Manifest Hash Already Consumed or Replay Blocked
**Symptom:**
```text
Approved manifest SHA-256 hash has already been consumed in a prior execution.
```
**Cause:**
The atomic execution ledger in `VERIFICATION.md` contains an entry for the provided SHA-256 hash. Manifest hashes can only be used once.

**Solution:**
Run `.\ClaudeCleanup.ps1 -Plan` to generate a fresh cleanup plan and obtain a new, unique SHA-256 hash.

---

### 2.8 WSL (Windows Subsystem for Linux) Isolation
**Symptom:**
WSL distributions and Linux `~/.claude` directories are reported in `-Audit`, but are not scheduled in `CLEANUP-PLAN.md`.

**Explanation:**
This is an intentional design invariant. Modifying ext4 virtual hard disks (`vhdx`) or running processes inside WSL distributions requires separate isolation and user authorization. The toolkit reports WSL state **read-only** and never touches Linux-side configuration.
To clean Claude inside WSL, open your WSL bash shell and manage `~/.claude` directly within Linux.
